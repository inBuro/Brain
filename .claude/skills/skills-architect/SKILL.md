# Skills Architect — пересборка среды в систему групп-мультискиллов

Скилл-реорганизатор. Берёт среду как есть — россыпь скиллов, агентов и заметок — и пересобирает её в трёхслойную архитектуру: группы-мультискиллы → подскиллы-оси → правила+принципы, с субагентами-аудиторами на проверяющих осях. Методология и шаблоны лежат внутри, в `references/` — скилл самодостаточен и работает в любой среде.

Главный закон: **система выводится из наполнения, а не наоборот.** У дизайнера получатся дизайн-оси, у маркетолога — контентные, у разработчика — инженерные. Количество групп, их имена, какие оси заслуживают аудиторов — всё решается по инвентаризации и интервью, а не по чужому образцу. Единственное, что переносится всегда, — сама механика трёх слоёв.

## Установка (для распространения)

Папку `skills-architect/` целиком положить в `~/.claude/skills/` (глобально) или `<проект>/.claude/skills/` (локально). Больше ничего не нужно: скилл триггерится сам и несёт методологию с собой.

## Инварианты (действуют во всех фазах)

1. **Ничего не удаляется.** Вытесненный скилл уезжает в `_archive/skills-retired-<дата>/` с пометкой, кто забрал его роль. Пенсия вместо удаления.
2. **Инструменты не перелопачиваются.** Скилл, внутри которого работающий софт (скрипты, движок, база, вендорный пак), при пересборке не переписывается — только обвязка снаружи. Развилка типов — в `references/methodology.md`.
3. **Апрув перед записью.** Фазы 1–3 read-only. Ни одного mv/write по скиллам владельца, пока он не подтвердил план.
4. **Один канон на знание.** Каждое повторяющееся знание получает одного носителя, остальные ссылаются. Второй канон не создаётся.
5. **Запись — в основном контексте.** Инвентаризацию (чтение) можно параллелить субагентами; пересборку (запись) делает только основной контекст, последовательно.
6. **Чужие правила не выбрасываются из-за непонятности.** Правило без внятного «почему» помечается и обсуждается с владельцем, а не тихо теряется.

## Протокол по фазам

**Фаза 0 · Предохранитель.** Если среда — git-репозиторий, зафиксировать состояние (commit или stash-снимок). Если нет — скопировать текущие `.claude/skills/` и `.claude/agents/` в `_archive/pre-architect-<дата>/`. Только после этого продолжать.

**Фаза 1 · Инвентаризация (read-only).** Собрать полную картину того, что есть:
- все места скиллов: `~/.claude/skills/`, `<проект>/.claude/skills/`, скиллы плагинов, локальные скиллы подпапок;
- агенты (`.claude/agents/`), CLAUDE.md всех уровней, слэш-команды, хуки;
- по каждому скиллу читается ТЕЛО, не только description (description часто врёт): что реально делает, размер, зависимости (скрипты, сеть, платные API, секреты), тип по развилке знание/инструмент/гибрид/приложение;
- кандидаты в дубли: скиллы об одном и том же, побайтовые копии, копии с дивергенцией.
Итог — таблица инвентаря: имя · где лежит · что делает · тип · размер · пересечения. Широкий сбор можно раздать read-only субагентам по местам поиска.

**Фаза 2 · Интервью с владельцем.** 3–5 вопросов, не больше: чем занимаешься (домены), какие задачи повторяются чаще всего, что сейчас бесит в работе со скиллами, есть ли отдельные проекты/среды со своими правилами, есть ли командные репозитории, которые трогать нельзя. Ответы определяют оси кластеризации.

**Фаза 3 · Проект архитектуры (главный артефакт).** Документ-план, по которому владелец принимает решение:
- **группы**: обычно 4–8, по доменам владельца; у каждой — имя, зона, список подскиллов из инвентаря;
- **внутри групп**: что становится осью со слитой логикой (несколько скиллов об одном — сливаются, роли источников разводятся картой тем), что остаётся процедурным подскиллом как есть, что инструмент (переезжает нетронутым);
- **карта дублей**: какие сливаются в какой канон, что уходит на пенсию;
- **аудиторы**: только для проверяющих/оценочных осей (ревью, аудит, детекция) — read-only субагент на ось; исполняющим осям аудитор не нужен;
- **принципы**: из правил владельца выводится слой «почему» (5–10 принципов на группу максимум); правила без принципа — списком на обсуждение;
- **исключения**: командные репо и среды, куда не лезем.
План показывается владельцу. Дальше — только после явного апрува; правки плана — новая итерация апрува.

**Фаза 4 · Пересборка.** По шаблонам из `references/templates.md`:
- физическая структура: `<группа>/SKILL.md` (роутер) + `<группа>/subskills/<имя>/`; на верхнем уровне `.claude/skills/` остаются ТОЛЬКО роутеры групп;
- роутеры: description с симптомами задач (триггерятся только они), таблица «задача → подскилл», режимы, дедуп-вахта;
- оси: слитая логика, карта тем «какая тема — какой источник главный», разрешённые конфликты строками арбитража;
- принципы: `references/principles.md` группы, правила получают ссылки на родительский принцип;
- аудиторы: `.claude/agents/<ось>-auditor.md`, каждый привязан к паре «правила + принципы» своей оси; для визуальных объектов — скрин-первый подход (рендер headless-браузером, суждение по картинке, код вторым слоем);
- карта скиллов: `SKILLS_MAP.md` (или секция в CLAUDE.md) — индекс групп и подскиллов;
- CLAUDE.md владельца: правило поиска скилла, правило двух вёдер, ссылка на протокол онбординга;
- протокол онбординга будущих скиллов ставится как подскилл инфраструктурной группы (текст-скелет в templates) — чтобы система не деградировала после первой же установки чужого пака.
Внутри переезжающих скиллов чинятся пути и фронтматтер (name = имя папки, честный description); у вложенных подскиллов снимается `disable-model-invocation` — он там бессмыслен.

**Фаза 5 · Верификация.**
- discovery: на верхнем уровне только роутеры, у каждого валидный фронтматтер name+description; вложенные SKILL.md сами НЕ триггерятся — это фича архитектуры, а не бага: система видит только роутеры, роутер читает подскиллы как файлы;
- пути: все ссылки внутри скиллов резолвятся (грепом по старым путям — ноль вне архива);
- счётчики карты сходятся с диском; скрипты инструментов запускаются; секретов в открытых файлах нет;
- мини-прогон: один запрос через роутер каждой группы доходит до нужного подскилла.
Любой FAIL чинится до зелёного.

**Фаза 6 · Передача.** Короткий итог владельцу: какие группы появились и почему такие, где что искать, как теперь ставить новые скиллы (только через онбординг), что уехало на пенсию и куда. Плюс список того, что осталось на его решение (правила без принципов, спорные слияния).

## Чего не делать

- Не копировать группы, имена и принципы из примеров methodology.md в чужую среду — они там как иллюстрация механики.
- Не создавать аудиторов «для всех осей подряд» — только проверяющим.
- Не сливать инструменты между собой и не «улучшать» их содержимое.
- Не трогать командные репозитории и среды из списка исключений.
- Не начинать пересборку без апрува плана и предохранителя фазы 0.

## Справочники скилла

- `references/methodology.md` — трёхслойная архитектура целиком: слои, правила↔принципы, аудиторы, правило двух вёдер, каноны, типология скиллов, онбординг.
- `references/templates.md` — скелеты всех файлов: роутер, ось, принципы, аудитор, карта скиллов, фрагмент CLAUDE.md, протокол онбординга.
