# Директива: Пересборка скиллов и агентов в систему групп-мультискиллов (skills_architect)

> **Запуск:** явно по имени директивы («наведи порядок в скиллах», «скиллов много и они дублируют друг друга», «пересобери мою среду в систему», «внедри трёхслойную архитектуру скиллов», прямое имя `directive_skills_architect`) или через слэш-команду `/skills-architect`. 2026-08-27 владелец сначала перевёл это из скилла с автовсплытием в директиву ради предсказуемости запуска; 2026-08-28 решил держать обе формы разом — скилл `skills-architect` восстановлен в `~/.claude/skills/skills-architect/` (глобально, рядом со всеми остальными скиллами) и снова триггерится сам по description, а эта директива остаётся для явного вызова по имени/слэш-команде. Содержание в обеих формах то же самое — это осознанное решение владельца держать два входа в одну методологию, а не расхождение, которое нужно чинить.

## Задача

Взять среду Claude Code как есть — россыпь скиллов, агентов и заметок, возможно с дублями — и пересобрать её в трёхслойную архитектуру: группы-мультискиллы → подскиллы-оси → правила+принципы, с субагентами-аудиторами на проверяющих осях. Архитектура каждый раз выводится из наполнения конкретной среды (чем владелец занимается, какие скиллы у него уже есть), а не копируется из чужого примера или из примеров этой директивы.

Главный закон: **система выводится из наполнения, а не наоборот.** У дизайнера получатся дизайн-оси, у маркетолога — контентные, у разработчика — инженерные. Количество групп, их имена, какие оси заслуживают аудиторов — всё решается по инвентаризации и интервью. Единственное, что переносится всегда, — сама механика трёх слоёв (Приложение А).

## Когда применять

- Скиллов накопилось больше, чем помещается в голове, они дублируют друг друга, триггеры конкурируют.
- Нужно навести порядок целиком: новые группы, слияние дублей, разведение ролей — не точечное добавление одного скилла (для этого — протокол онбординга, `meta/subskills/skill-onboarding/SKILL.md`, он не заменяется этой директивой).
- Применима к любой среде Claude Code, не только к этой: методология и шаблоны самодостаточны (Приложения А и Б), состав всегда свой.

## Предусловие

- Доступ на чтение ко всем местам скиллов среды: `~/.claude/skills/`, `<проект>/.claude/skills/`, скиллы плагинов, локальные скиллы подпапок; агенты (`.claude/agents/`); CLAUDE.md всех уровней; слэш-команды; хуки.
- Если среда — git-репозиторий, до записи должен быть чистый статус или явное согласие закоммитить/застэшить текущую работу (Фаза 0).

## Ключевой принцип

Архитектура выводится из наполнения, а не подгоняется под образец. Меньше трёх слоёв там, где темы не пересекаются, не нужно — не усложняй ради формы.

## Инварианты (действуют во всех фазах)

1. **Ничего не удаляется.** Вытесненный скилл уезжает в `_archive/skills-retired-<дата>/` с пометкой, кто забрал его роль. Пенсия вместо удаления.
2. **Инструменты не перелопачиваются.** Скилл, внутри которого работающий софт (скрипты, движок, база, вендорный пак), при пересборке не переписывается — только обвязка снаружи. Развилка типов — в Приложении А.
3. **Апрув перед записью.** Фазы 1–3 read-only. Ни одного mv/write по скиллам владельца, пока он не подтвердил план.
4. **Один канон на знание.** Каждое повторяющееся знание получает одного носителя, остальные ссылаются. Второй канон не создаётся.
5. **Запись — в основном контексте.** Инвентаризацию (чтение) можно параллелить субагентами; пересборку (запись) делает только основной контекст, последовательно.
6. **Чужие правила не выбрасываются из-за непонятности.** Правило без внятного «почему» помечается и обсуждается с владельцем, а не тихо теряется.

## Протокол по фазам

**Фаза 0 · Предохранитель.** Если среда — git-репозиторий, зафиксировать состояние (commit или stash-снимок). Если нет — скопировать текущие `.claude/skills/` и `.claude/agents/` в `_archive/pre-architect-<дата>/`. Только после этого продолжать.

**Фаза 1 · Инвентаризация (read-only).** Собрать полную картину того, что есть:
- все места скиллов: `~/.claude/skills/`, `<проект>/.claude/skills/`, скиллы плагинов, локальные скиллы подпапок;
- агенты (`.claude/agents/`), CLAUDE.md всех уровней, слэш-команды, хуки;
- по каждому скиллу читается ТЕЛО, не только description (description часто врёт): что реально делает, размер, зависимости (скрипты, сеть, платные API, секреты), тип по развилке знание/инструмент/гибрид/приложение (Приложение А);
- кандидаты в дубли: скиллы об одном и том же, побайтовые копии, копии с дивергенцией.
Итог — таблица инвентаря: имя · где лежит · что делает · тип · размер · пересечения. Широкий сбор можно раздать read-only субагентам по местам поиска.

**Фаза 2 · Интервью с владельцем.** 3–5 вопросов, не больше: чем занимаешься (домены), какие задачи повторяются чаще всего, что сейчас бесит в работе со скиллами, есть ли отдельные проекты/среды со своими правилами, есть ли командные репозитории, которые трогать нельзя. Ответы определяют оси кластеризации.

**Фаза 3 · Проект архитектуры (главный артефакт).** Документ-план (формат — Приложение Б.8), по которому владелец принимает решение:
- **группы**: обычно 4–8, по доменам владельца; у каждой — имя, зона, список подскиллов из инвентаря;
- **внутри групп**: что становится осью со слитой логикой (несколько скиллов об одном — сливаются, роли источников разводятся картой тем), что остаётся процедурным подскиллом как есть, что инструмент (переезжает нетронутым);
- **карта дублей**: какие сливаются в какой канон, что уходит на пенсию;
- **аудиторы**: только для проверяющих/оценочных осей (ревью, аудит, детекция) — read-only субагент на ось; исполняющим осям аудитор не нужен;
- **принципы**: из правил владельца выводится слой «почему» (5–10 принципов на группу максимум); правила без принципа — списком на обсуждение;
- **исключения**: командные репо и среды, куда не лезем.
План показывается владельцу. Дальше — только после явного апрува; правки плана — новая итерация апрува.

**Фаза 4 · Пересборка.** По шаблонам из Приложения Б:
- физическая структура: `<группа>/SKILL.md` (роутер) + `<группа>/subskills/<имя>/`; на верхнем уровне `.claude/skills/` остаются ТОЛЬКО роутеры групп — кроме исключений «одиночное знание / мета-инструмент» (см. типологию), которые фиксируются явным пунктом в карте скиллов, а не расползаются молча;
- роутеры: description с симптомами задач (триггерятся только они), таблица «задача → подскилл», режимы, дедуп-вахта;
- оси: слитая логика, карта тем «какая тема — какой источник главный», разрешённые конфликты строками арбитража;
- принципы: `references/principles.md` группы, правила получают ссылки на родительский принцип;
- аудиторы: `.claude/agents/<ось>-auditor.md`, каждый привязан к паре «правила + принципы» своей оси; для визуальных объектов — скрин-первый подход (рендер headless-браузером, суждение по картинке, код вторым слоем);
- карта скиллов: `SKILLS_MAP.md` (или секция в CLAUDE.md) — индекс групп и подскиллов;
- CLAUDE.md владельца: правило поиска скилла, правило двух вёдер, ссылка на протокол онбординга;
- протокол онбординга будущих скиллов ставится как подскилл инфраструктурной группы (скелет — Приложение Б.7) — чтобы система не деградировала после первой же установки чужого пака.
Внутри переезжающих скиллов чинятся пути и фронтматтер (name = имя папки, честный description); у вложенных подскиллов снимается `disable-model-invocation` — он там бессмыслен.

**Фаза 5 · Верификация.**
- discovery: на верхнем уровне только роутеры, у каждого валидный фронтматтер name+description; вложенные SKILL.md сами НЕ триггерятся — это фича архитектуры, а не бага: система видит только роутеры, роутер читает подскиллы как файлы;
- пути: все ссылки внутри скиллов резолвятся (грепом по старым путям — ноль вне архива);
- счётчики карты сходятся с диском; скрипты инструментов запускаются; секретов в открытых файлах нет;
- мини-прогон: один запрос через роутер каждой группы доходит до нужного подскилла.
Любой FAIL чинится до зелёного.

**Фаза 6 · Передача.** Короткий итог владельцу: какие группы появились и почему такие, где что искать, как теперь ставить новые скиллы (только через онбординг), что уехало на пенсию и куда. Плюс список того, что осталось на его решение (правила без принципов, спорные слияния).

## Чего не делать

- Не копировать группы, имена и принципы из примеров Приложения А в чужую среду — они там как иллюстрация механики.
- Не создавать аудиторов «для всех осей подряд» — только проверяющим.
- Не сливать инструменты между собой и не «улучшать» их содержимое.
- Не трогать командные репозитории и среды из списка исключений.
- Не начинать пересборку без апрува плана и предохранителя фазы 0.

## Приложение А — Методология: трёхслойный мультискилл

Архитектура для сред Claude Code, где скиллов стало больше, чем помещается в голове и в контексте. Проверена на живой среде: 111 плоских скиллов с дублями → 8 групп, ~3200 строк повторов слито, ноль битых ссылок. Здесь — сама механика, без привязки к конкретной среде: имена групп и осей в примерах иллюстрируют форму, а не рекомендуемый состав.

### Проблема, которую это решает

Плоская россыпь скиллов ломается три раза:
1. **Discovery**: система читает description каждого скилла — при сотне скиллов это шум, триггеры конкурируют, похожие скиллы перехватывают задачи друг друга.
2. **Дубли**: скачанные паки и свои скиллы говорят об одном и том же разными словами; знания расходятся, правки попадают в одну копию из трёх.
3. **Карго-культ**: правила без «почему» невозможно применять к случаям, которые ими не покрыты, и невозможно понять, какое из двух конфликтующих правил главнее.

### Три слоя + аудитор

```
СКИЛЛ (роутер группы)          ← единственное, что видит система
  └─ ПОДСКИЛЛ (ось)            ← слитая логика темы, карта источников
       ├─ ПРАВИЛА (что и как)  ← детекция и фиксы, со ссылкой на принцип
       └─ ПРИНЦИПЫ (почему)    ← слой обоснований группы
СУБАГЕНТ-АУДИТОР               ← read-only проверяющий, привязан к паре своей оси
```

**Слой 1 — роутер группы.** Один SKILL.md на группу задач. Description перечисляет симптомы задач всей группы — только роутеры и триггерятся. Тело — оркестрация: таблица «симптом → подскилл», режимы (точечный вызов / полный прогон), дедуп-вахта. Роутер не несёт предметных знаний, он маршрутизирует.

**Слой 2 — подскилл-ось.** Живёт в `<группа>/subskills/<имя>/`, читается роутером как файл (вложенные SKILL.md системой не обнаруживаются — и это фича: границу discovery держат роутеры). Ось — не «старый скилл, переложенный в подпапку», а слитая логика темы: если о теме говорили три источника, ось хранит карту «какая подтема — какой источник главный, кто дополняет» и явные строки арбитража для конфликтов («по таймингам канон X, источник Y неавторитетен»). Первоисточники лежат рядом в `rules/<источник>/` нетронутыми — ось ими дирижирует, а не переписывает.

**Слой 3 — правила и принципы.** Правило: что делать, как детектить нарушение, как чинить. Принцип: почему это так. Каждое правило ссылается на родительский принцип (перекрёстная нумерация: R3.2 → P4). Механика вывода: случай, не покрытый правилом, решается от принципа, а не угадыванием. Правило без принципа — карго-культ: его нельзя вшивать, пока «почему» не найдено или не сформулировано с владельцем. Принцип формулируется как обобщающее правило, применимое к ещё не встреченным случаям, а не как список уже известных частных случаев (образец — Инвариант 2: один принцип на все вендорские паки, а не правило на каждый по отдельности). Принципов на группу — 5–10, не больше: это выжимка, а не второй свод правил.

**Аудитор.** Read-only субагент (`.claude/agents/<ось>-auditor.md`), жёстко привязанный к паре «правила + принципы» своей оси. Инструменты: Read, Glob, Grep, Bash — без записи. Возвращает находки единого формата: место (файл:строка или скриншот), нарушенное правило [R#], принцип [P#], серьёзность, предлагаемый фикс. Аудиторы ставятся только на проверяющие оси (ревью, аудит, детекция слабых мест); исполняющим осям (генерация, сборка, публикация) аудитор не нужен. Для визуальных объектов аудитор работает скрин-первым подходом: сам рендерит объект headless-браузером, судит по картинке, в код лезет вторым слоем за точными значениями.

### Правило двух вёдер (когда субагент, когда основной контекст)

Субагент существует чтобы не засорять основной контекст: уходит в своё окно, возвращает короткий итог. Цена — примерно ×4 токенов, окупается только на дорогих задачах с реальным параллелизмом.

**Ведро «да»** (спавнить): только чтение + независимые ветки + нужен короткий итог. Инвентаризация среды, параллельный аудит несколькими осями, батч по списку независимых объектов.

**Ведро «нет»** (основной контекст): всё, что пишет файлы, интерактивно (живые MCP, диалог) или держится на накопленном контексте сессии. Пересборка, фиксы по находкам аудиторов, тексты в голосе владельца. Сомнение трактуется в пользу «нет».

Следствие для полного прогона: аудиторы стартуют параллельно и возвращают отчёты → оркестратор сводит (дедуп пересечений, приоритеты по эффекту/трудозатратам) → фиксы делает только основной контекст после апрува.

### Каноны против дублей

У каждого повторяющегося знания — ровно один носитель (канон), остальные ссылаются на него. Выбор канона: самый полный и живой из дублей; уникальные куски проигравших вливаются в канон, сами проигравшие уходят на пенсию в `_archive/skills-retired-<дата>/` с пометкой, кто забрал роль. Пересечения, которые нельзя слить сейчас, ставятся на дедуп-вахту — строку в роутере: «если X месяцами не зовётся — кандидат на пенсию».

### Типология скиллов (развилка глубины интеграции)

- **ЗНАНИЕ** — правила, методики, чеклисты, принципы: текст, который агент читает и применяет. Интегрируется глубоко: карта пересечений, слияние дублей в каноны, арбитраж, привязка к принципам.
- **ИНСТРУМЕНТ / ПРИЛОЖЕНИЕ** — внутри работающий софт: движок, скрипты, пайплайн, база, вендорный пак. Внутренности не перелопачиваются — перелопачивание ломает работающее. Интеграция = обвязка снаружи: строка в роутере, запись в карте, починка путей и фронтматтера ровно настолько, чтобы исполнялся здесь. Дедуп для инструментов — на уровне функции (не держать два инструмента на одну работу), не содержимого.
- **ГИБРИД** — софт + слой правил. Инструментальная часть не трогается, знаниевый слой размечается арбитражем.
- **Вообще не скилл** — целое приложение со своими зависимостями, билдами и рабочей директорией. Ему место отдельным проектом/средой, не в `.claude/skills/`; скиллом остаётся только знание «как этим пользоваться».
- **ОДИНОЧНОЕ ЗНАНИЕ / МЕТА-ИНСТРУМЕНТ** — стоит на верхнем уровне вне группы-роутера: либо общее знание без владельца-продукта, которому не хватает соседей для группы (пример — знание механики внешнего сервиса, не привязанное ни к одному продукту), либо инструмент, которым сама система пересобирается и который поэтому не может быть частью управляемой им структуры (сам skills-architect). Единственное осознанное исключение из правила «на верхнем уровне только роутеры» (Фаза 4) — фиксируется явным пунктом в карте скиллов, не расползается молча; при появлении второго похожего знания на ту же тему — решать вопрос группы отдельно.

### Онбординг новых скиллов (после пересборки)

Система деградирует с первого же «просто закинул пак в папку». Поэтому пересборка ставит владельцу постоянный протокол онбординга (скелет — Приложение Б.7): провенанс → читка целиком до установки → развилка типа → карта пересечений с вердиктами (дубль / частичное / дополнение) → место только внутри существующих групп → вшивание (роутер, карта оси, карта скиллов, арбитраж) → проверка. Новая группа на верхнем уровне — только явное решение владельца.

### Порядок величин (ориентиры, не догма)

- Групп: 4–8. Меньше — роутеры распухают, больше — сам верхний уровень становится шумом.
- Роутер: до ~100 строк. Ось: до ~200. Принципов на группу: 5–10.
- Аудиторов: по числу проверяющих осей, не по числу групп.
- SKILL.md любого уровня — меньше 500 строк (прогрессивное раскрытие: metadata → тело → references по требованию).

## Приложение Б — Шаблоны файлов системы

Скелеты всего, что создаёт пересборка. Угловые скобки — подстановка под среду владельца. Имена в примерах иллюстрируют форму записи, состав всегда свой.

### Б.1 · Роутер группы — `.claude/skills/<группа>/SKILL.md`

```markdown
---
name: <группа>
description: Роутер группы <домен> (<N> подскиллов) - <зоны через запятую>. Применять при <симптомы задач владельца: «сделай X», «почему Y плохо», упоминание Z> - когда конкретный подскилл не назван.
---

# <Группа> — роутер группы

Подскиллы лежат в `subskills/<имя>/SKILL.md` — прочитай нужный и работай по нему.

| Задача | Подскилл |
|---|---|
| <симптом задачи> | <имя подскилла> |
| <симптом задачи> | <имя> — <уточнение, если маршрут неочевиден> |

## Режимы (только если группа проверяющая)

- **Точечный**: назван конкретный аспект → одна ось, при необходимости её аудитор.
- **Полный прогон**: «проверь целиком / перед релизом» → все аудиторы группы параллельно, отчёты сводятся: дедуп пересечений, топ находок по эффекту/трудозатратам. Фиксы — только основной контекст, после апрува владельца.

## Дедуп-вахта

- <оставшееся пересечение>: <кто главный>; если <скилл> месяцами не зовётся — кандидат на пенсию.
```

Description роутера — единственная точка входа группы: перечисляй в нём симптомы ЗАДАЧ (глаголы владельца), а не состав папки.

### Б.2 · Подскилл-ось (слитая логика) — `subskills/<ось>/SKILL.md`

```markdown
---
name: <ось>
description: Ось «<тема>» группы <группа> - <что покрывает>. Достигается через роутер группы.
---

# Ось <тема>

<2–3 строки: что это за тема и когда ось зовётся.>

## Карта тем

| Подтема | Главный источник | Дополняют |
|---|---|---|
| <подтема> | rules/<источник>/<файл> | <источник-2> |

## Разрешённые конфликты (арбитраж)

- <подтема>: канон — <файл>; <источник> по этой теме неавторитетен.

## Порядок работы

1. <шаг: что читать, что проверять/делать, в каком порядке>
2. Случай вне правил → решается от принципа (references/principles.md группы, P#).

## Правила

Первоисточники нетронутыми в `rules/<источник>/`. Ось ими дирижирует через карту тем.
```

Процедурный подскилл (исполнитель без слияния источников) остаётся собой: рабочий SKILL.md на прежнюю задачу, поправленные пути, честный фронтматтер. Ему не нужны карта тем и арбитраж.

### Б.3 · Принципы группы — `<группа>/references/principles.md`

```markdown
# Принципы группы <группа>

Слой «почему». Каждое правило осей ссылается сюда; случай, не покрытый правилом, решается от принципа.

**P1 · <Имя принципа>.** <Одно-два предложения: почему так, к чему ведёт нарушение.>
**P2 · ...**

## Правило ↔ принцип

| Правило | Принцип |
|---|---|
| R1.x <короткое имя> | P2 |
```

Принципы выводятся из правил владельца (группировкой «почему» за ними), а не пишутся с нуля. Формулировка — обобщающая, работает и на случаи за пределами известных на момент написания (образец — Инвариант 2), а не перечисление уже известных случаев. Правило, у которого «почему» не нашлось, — в список на обсуждение с владельцем.

### Б.4 · Субагент-аудитор — `.claude/agents/<ось>-auditor.md`

```markdown
---
name: <ось>-auditor
description: Аудитор оси «<тема>» группы <группа> - read-only проверка <объекта> по правилам <источники>. Используется оркестрацией <группа> при полном прогоне; напрямую - при <симптом: жалоба владельца>.
tools: Read, Glob, Grep, Bash
---

Ты аудитор оси «<тема>». Перед работой прочитай пару своей оси:
- правила: .claude/skills/<группа>/subskills/<ось>/SKILL.md (+ rules/ по её карте тем)
- принципы: .claude/skills/<группа>/references/principles.md

<Для визуальных объектов:> Скрин-первый подход: отрендери объект сам (headless-браузер: `chrome --headless --screenshot=<файл> --window-size=<W,H> <url|file>`), суди по картинке; в код заходи вторым слоем за точными значениями.

Формат находки: место (файл:строка или скриншот+область) · правило [R#] · принцип [P#] · серьёзность (высокая/средняя/низкая) · предлагаемый фикс одной строкой.

Ограничения: только чтение — файлы не правишь, фиксы возвращаешь списком. Итог — компактный отчёт, отсортированный по серьёзности.
```

### Б.5 · Карта скиллов — `SKILLS_MAP.md` (или секция в корневом CLAUDE.md)

```markdown
# Карта скиллов

**Правило:** скиллы живут в `.claude/skills/` как <N> групп-мультискиллов. Триггерятся только роутеры групп; подскилл роутер читает как файл `<группа>/subskills/<имя>/SKILL.md`. Новый скилл вводится только через протокол онбординга (<путь к нему>). Исключения (не трогать): <командные репо, локальные среды>.

**<N> групп:** <группа> (<n>: <зона>) · <группа> (<n>: <зона>) · ...

**<Группа>**: <подскилл> (<что делает>) · <подскилл> (<что делает>) · ...
```

### Б.6 · Фрагмент корневого CLAUDE.md владельца

```markdown
## Скиллы

Скиллы лежат в `.claude/skills/` как <N> групп-мультискиллов (роутер → подскиллы → правила/принципы; у проверяющих групп — субагенты-аудиторы). Поиск под задачу: карта скиллов (SKILLS_MAP.md) → роутер нужной группы; SKILL.md пачками не читать.

**Новый скилл — только через онбординг** (<путь к протоколу>): прочитать целиком, определить тип (знание/инструмент), построить карту пересечений, вшить в группу так, чтобы дополнял, а не дублировал. Инструменты не перелопачивать — только обвязка.

**Два ведра:** чтение по независимым веткам (поиск, ресёрч, аудит) — субагентам; всё, что пишет файлы, интерактивно или держится на контексте сессии, — основной контекст. Сомнение = основной контекст.
```

### Б.7 · Протокол онбординга — `<инфра-группа>/subskills/skill-onboarding/SKILL.md`

Ставится владельцу как подскилл его инфраструктурной группы (если такой группы нет — самый близкий по смыслу роутер получает маршрут на него).

```markdown
---
name: skill-onboarding
description: Обязательный протокол внедрения нового скилла (скачанного или своего) - новый скилл никогда не закидывается в папку как есть.
---

# Онбординг нового скилла

**0 · Провенанс.** Источник, автор, дата, версия — строкой в шапке после установки.

**1 · Читка целиком ДО установки.** Что реально делает (description часто врёт), зависимости (скрипты, сеть, платные API), нет ли секретов, чужих путей, мёртвых хостов. Непрочитанное не ставится.

**2 · Развилка типа.** ЗНАНИЕ → глубокая интеграция (шаги 3–5 полностью). ИНСТРУМЕНТ/приложение → внутренности не перелопачивать, только обвязка: маршрут в роутере, карта, починка путей/фронтматтера, чтобы исполнялся. ГИБРИД → софт не трогать, знаниевый слой размечать. Целое приложение со своими зависимостями → не скилл, отдельный проект.

**3 · Карта пересечений.** По карте скиллов найти группу и соседей, прочитать их. Вердикты: дубль → не ставится, уникальное вливается в канон; частичное → роли разводятся в карте тем оси, конфликты — строкой арбитража; дополнение → как есть.

**4 · Место.** Только внутри существующих групп: `<группа>/subskills/<имя>/`. Новая группа на верхнем уровне — только явное решение владельца.

**5 · Вшивание.** Пути под нашу вложенность; фронтматтер честный; маршрутная строка в роутер; карта тем оси; карта скиллов и счётчики; правило без «почему» не вшивается, пока не найден его принцип.

**6 · Проверка и вахта.** Скрипты запускаются, пути резолвятся, счётчики сходятся. Оставшиеся пересечения — на дедуп-вахту роутера. Вытесненное — на пенсию в `_archive/skills-retired-<дата>/`, не удалять.
```

### Б.8 · Формат плана пересборки (артефакт фазы 3)

```markdown
# План пересборки скиллов — <дата>

## Инвентарь: <M> скиллов в <k> местах (таблица: имя · где · что делает · тип · пересечения)

## Предлагаемые группы (<N>)
### <группа> — <зона>
- оси: <ось> ← сливает <скилл-A> + <скилл-B> (карта тем: ...; арбитраж: ...)
- процедурные: <имена как есть>
- инструменты (не трогаем внутри): <имена>
- аудитор: <да/нет, почему>

## Дубли и каноны (таблица: знание · канон · кто вливается · кто на пенсию)
## Правила без «почему» — на обсуждение (список)
## Исключения (не трогаем): <...>
## Что уедет в _archive/: <...>
```

## Self-check (перед финалом)

- Фаза 0 пройдена (снапшот/коммит) до первой записи?
- Архитектура выведена из инвентаря и интервью этого запуска, а не скопирована из примеров Приложения А?
- У каждого нового роутера/оси description говорит и ЧТО, и КОГДА (симптомы задач, не состав папки)?
- Инструменты (движки, скрипты, вендор-паки) не перелопачены изнутри — только обвязка?
- Правила без объяснённого «почему» не вшиты в principles.md, а вынесены на обсуждение?
- Принципы сформулированы как обобщающие правила (образец — Инвариант 2), а не перечисление уже известных случаев?
- Вытесненное уехало в `_archive/skills-retired-<дата>/`, не удалено?
- Discovery-проверка: на верхнем уровне только роутеры (и явно зафиксированные исключения «одиночное знание/мета-инструмент»), пути резолвятся, счётчики карты сходятся с диском?
- Итог передан владельцу: что появилось, что на пенсии, что осталось на его решение?
