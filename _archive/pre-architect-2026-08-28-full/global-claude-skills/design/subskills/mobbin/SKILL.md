# Mobbin MCP

Нужен агенту в двух режимах:
1. **Разовая установка** — когда пользователь впервые подключает Mobbin MCP
2. **Постоянная работа** — агент обращается к этому навыку каждый раз, когда ищет UI/UX референсы через Mobbin

---

## Установка (один раз)

**Всегда через правку `~/.claude.json`.** Не вызывай `claude mcp add` — CLI может отсутствовать в PATH (агент часто работает внутри VSCode-расширения, там standalone CLI нет). Ручная правка конфига универсальна и не требует отдельного бинарника.

**Шаг 1.** Прочитай `~/.claude.json`. Если на этот файл нет разрешения — попроси пользователя добавить read/write allow-правило на `~/.claude.json` в настройках Claude Code (`/permissions` или `.claude/settings.json`), потом продолжай.

**Шаг 2.** Найди в файле объект `mcpServers` (верхний уровень). Если его нет — создай. Добавь туда запись:

```json
"mobbin": {
  "type": "http",
  "url": "https://api.mobbin.com/mcp"
}
```

Если запись `mobbin` уже есть — не перезаписывай молча, покажи пользователю текущее значение и спроси.

**Шаг 3.** Сохрани файл. Скажи пользователю:

> Перезапусти VSCode-расширение Claude Code (или desktop-приложение), чтобы оно подцепило новый MCP-сервер. Вернись сюда и напиши «готово».

**Шаг 4.** После подтверждения вызови любой из трёх инструментов (например `search_screens` с простым запросом) — если сервер настроен верно, вернутся результаты без дополнительного OAuth-шага (Mobbin MCP работает по обычному http-соединению).

## Постоянная работа: справочник инструментов

Три read-only поисковых инструмента. Все ищут по натуральному языку и возвращают картинки прямо в ответе — модель обязана **разглядывать сами изображения**, а не полагаться только на метаданные при описании результата пользователю.

### `search_flows` — многошаговые пользовательские флоу

Например: онбординг, чекаут. Возвращает превью с равным шагом по флоу + метаданные по каждому экрану.

| Параметр | Обязателен | Значения | Заметки |
|---|---|---|---|
| `query` | да | текст | один флоу за раз — шаги и что видно по пути. Не объединять несколько флоу в одном запросе, не использовать отрицания и расплывчатые «modern/clean». Можно указать конкретное приложение («Duolingo onboarding»). Платформу в query не пишем — для неё свой параметр |
| `platform` | да | `ios` \| `web` | |
| `limit` | нет | 1–10, default 5 | меньше лимит — меньше контекста |
| `page` | нет | 1–20, default 1 | пагинация |
| `image_format` | нет | `webp` (default) \| `jpg` | `jpg`, если клиент не поддерживает webp |

На хостах с MCP Apps дополнительно рендерит интерактивную галерею результатов.

### `search_screens` — отдельные UI-экраны

| Параметр | Обязателен | Значения | Заметки |
|---|---|---|---|
| `query` | да | текст | один экран за раз — элементы UI и как они связаны. Пример: «login screen with biometric authentication». Не объединять несколько экранов/интентов, без отрицаний («without ads»), без расплывчатых стилевых слов |
| `platform` | да | `ios` \| `web` | |
| `mode` | нет | `deep` (default) \| `standard` \| `fast` | `deep` — AI-пайплайн, интерпретирует интент и скорит релевантность (для нюансных запросов); `standard` — низкая задержка; `fast` — deprecated-алиас `standard`, использовать `standard` |
| `limit` | нет | 1–30, default 20 | больше — больше контекста |
| `exclude_screen_ids` | нет | массив UUID, до 100 | исключить уже виденные экраны |
| `image_format` | нет | `webp` (default) \| `jpg` | |

**Обязательное правило цитирования:** у каждого экрана есть `mobbin_url` — каноническая ссылка на Mobbin. При показе результатов пользователю ВСЕГДА давать markdown-ссылку на `mobbin_url` для каждого упомянутого экрана.

### `search_sections` — секции сайтов (web only)

Например: About, Pricing, Footer.

| Параметр | Обязателен | Значения | Заметки |
|---|---|---|---|
| `query` | да | текст | одна секция за раз — контент и элементы. Пример: «pricing page with plan comparison table». Без объединения секций, без отрицаний, без расплывчатых стилевых слов |
| `limit` | нет | 1–30, default 20 | |
| `page` | нет | ≥1, default 1 | пагинация |
| `image_format` | нет | `webp` (default) \| `jpg` | |

Платформы у `search_sections` нет параметра — только web-секции.

## Сценарии использования (сверено с офиц. доками + practitioner-разборами)

Три тула — это примитивы. Всё ниже строится на них через несколько запросов + мой синтез поверх (и, где отмечено, другие тулы: WebSearch/WebFetch, Figma MCP, frontend-design). Источники внизу файла.

**Reference scouting**
- Industry sweep — «покажи 10 fintech-онбордингов» → `search_flows`/`search_screens` с `limit` побольше
- Style sweep — «дай тёмные editorial-портфолио», «неубрутализм в маркетинг-страницах» — конкретный стиль/эстетика в query
- Mash-up — беру 2-3 референса разными запросами, сама собираю гибрид (спека или сразу код через frontend-design)

**Component-level deep dive**
- «Покажи 10 empty state / 10 paywall / 10 settings-страниц» рядом — сравнительный обзор одного и того же элемента
- Swipe file — серия запросов по одному элементу, свожу в один документ/доску
- Edge cases — прицельный query на loading skeleton, permission prompt, error state, end-of-list

**Build from references (основной цикл)**
- Ищу референсы → синтезирую паттерны → строю гибрид в коде/спеке, объясняя какая деталь откуда
- Competitive teardown — то же + WebSearch/WebFetch, чтобы разобрать реальные сайты конкурентов, не только скриншоты Mobbin

**Pattern & trend research**
- «Что сейчас все делают в героях/онбординге/auth в категории X» — свожу доминирующие паттерны по серии запросов
- Color story / typography study — ищу приложения с конкретной палитрой/шрифтовым решением, чтобы подтвердить или уточнить бренд-направление

**Critique & audit**
- Показываю референсы «лучше в классе» к текущему экрану пользователя, разбираю чем они сильнее
- Side-by-side с чужим продуктом («сравни мою posting-страницу с типичными B2B-лендингами») — сильные/слабые стороны + приоритизированные рекомендации
- **С Figma MCP разом**: аудит живого дизайна против индустрийных паттернов, потом редизайн и экспорт результата обратно в Figma

**Research-before-build gate** (паттерн из практики, не мой стандартный режим, но полезен для больших задач)
- Сначала отчёт: релевантные референсы + сходящиеся паттерны + fit-анализ + предлагаемая структура — без кода
- Затем 5 уточняющих вопросов, которые реально меняют архитектуру/контент
- Строю только после подтверждения плана

**Copywriting/microcopy**
- «Какие паттерны помогают юзеру быстрее восстановиться после ошибки» → сравнение default vs улучшенной копи с примерами из живых продуктов

Комбинация с image-gen (генерация кастомного варианта картинки по референсу) в моём тулсете сейчас недоступна — вместо этого я беру референс и сразу строю рабочий код (HTML/React) в его стилистике через frontend-design.

## Правила работы для агента

**Один запрос — один флоу/экран/секция.** Не комбинировать несколько разных объектов в одном `query` — искать раздельно и сравнивать результаты.

**Смотреть на картинки, не только на метаданные.** Все три тула прямым текстом требуют разглядывать возвращённые изображения перед тем, как описывать их пользователю.

**Специфичность запроса решает.** «Checkout with payment method selection» лучше, чем «nice checkout». Конкретное приложение в query сужает выборку до него.

**Ссылки обязательны для экранов.** Каждый `search_screens`-результат, который попадает в ответ пользователю, сопровождается markdown-ссылкой на его `mobbin_url`.
