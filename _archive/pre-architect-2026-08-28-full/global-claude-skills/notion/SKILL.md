# Notion — механика работы через MCP

Общая для любого проекта механика: как физически вести работу с Notion-страницами через MCP-тулы — структура, опасные операции, грабли конкретно этого интеграционного слоя. Голос текста и сценарий конкретного ревью-цикла (кто с кем согласовывает, какой гейт перед правкой кода) — не сюда, это уровень проектного подскилла, который на эту механику ссылается.

Собран 2026-08-27 из механики, накопленной на кейсе Beefy (`portfolio/subskills/notion-review`); вынесен в глобальный канон, потому что грабли API и конвенции структуры страниц не специфичны для одного проекта — та же механика нужна в любой другой Notion-работе (Fadercraft, Bifi, Dynamic Focus и т.д.).

## Структура страниц: не одна куча

- **Каждый H2 значимой страницы — отдельная дочерняя Notion-страница.** H1 не трогается, H3+ остаётся инлайн. Это default-on, не разовая просьба.
- **Хаб/родитель держит только ссылки на детей**, никакого содержимого напрямую. Notion сам рисует список дочерних страниц — свой ручной bullet-список ссылок поверх этого создаёт видимый дубль.
- **Медиа — только через `notion-create-attachment`.** Presigned S3-ссылка из `notion-fetch` живёт ~5 минут; если вставить её напрямую в markdown `create-pages`/`update-page`, картинка может не догрузиться асинхронно и молча остаться пустой. Сначала `create-attachment` с `source_url` (синхронная закачка), потом `<image src="file-upload://<id>">`.

## Опасность: `allow_deleting_content: true`

Почти никогда не ставить `true` на `replace_content`/`update_content`. Если инструмент требует флаг из-за существующих дочерних страниц — это сигнал сузить правку (`update_content` точечным search-replace), а не подтвердить удаление рефлекторно. Прецедент: банер на месте контента хаба стёр дочерние главы целиком за один вызов.

## Механика API — грабли этого интеграционного слоя

- **`notion-get-comments` без `discussion_id` часто возвращает `{}`**, даже когда на странице реально есть открытые треды. Сначала `notion-fetch` с `include_discussions: true` — он даёт `<page-discussions>` со списком `discussion://...` ID (в `<example-discussions>` не все, если тредов много — остальные видны через `discussion-urls=` атрибуты на самих абзацах в `<content>`). Дальше — `notion-get-comments` с explicit `discussion_id` по каждому.
- **`update_content` со старым текстом внутри нумерованного/маркированного списка — не включать литеральные «1. », «2. », «- » в начало `old_str`.** Notion хранит это как тип блока (numbered-list-item/bulleted-list-item), не как текст — цифра/дефис не часть содержимого блока, совпадение не найдётся. Матчить с текста самого пункта.
- **Жирный текст (`**...**`) в `old_str` тоже может не совпасть**, если границы bold-разметки в реальном хранимом rich-text не совпадают с тем, что вернул `fetch` в виде markdown (особенно когда bold накрывает только часть предложения, а не целиком). Если совпадение падает — убрать `**` из `old_str` и матчить голый текст, или разбить на несколько меньших `update_content` вызовов.
- **Батч из нескольких `content_updates` в одном вызове падает атомарно на первой же несовпавшей записи** — сообщение об ошибке иногда конкатенирует куски нескольких `old_str` вперемешку, что сбивает с толку. Если батч из 3+ правок падает необъяснимо — разбивать по одной правке за вызов, находить виновника.
- **После `update_content`, оставляющего пустой пункт списка** (например, стёр текст, но не убрал сам пункт-обёртку) — следующий `fetch` покажет голое «1.\n2. Текст...». Это надо чистить отдельным проходом: убрать `"1.\n"` (с переводом строки) как `old_str`, `new_str: ""`.
- **Токен интеграции (`~/.config/notion/env`) читать и использовать только в ОДНОМ вызове Bash.** Shell-состояние не сохраняется между отдельными вызовами тула — если прочитать токен в одном вызове и вписать его буквальное значение в команду следующего, значение целиком попадает в транскрипт тула. Уже случалось трижды. Безопасные варианты: Python-скрипт с `open()` внутри одного процесса, либо один shell-вызов с цепочкой `TOKEN=$(grep -oP 'NOTION_TOKEN=\K.*' ~/.config/notion/env) && curl -H "Authorization: Bearer $TOKEN" ...`. Никогда не печатать токен целиком или срезом (`token[:8]`, `cut -c1-20` и т.п.) «чтобы проверить, что загрузился» — это тоже утечка байтов секрета; для проверки годится только `len(token) > 0`/`bool(token)`.

## Триггерные фразы (голосовой ввод шумный)

Всё это значит «иди читай Notion и работай с ним» — по контексту задачи, не обязательно ревью:
- «ношн», «ноушен», «ношун», «ношне» (падежные/дикт-искажения слова Notion)
- «откомментил», «прошёлся по [Notion]», «ответил на комментарии»
- «внеси, ответь», «ответь и внеси»
