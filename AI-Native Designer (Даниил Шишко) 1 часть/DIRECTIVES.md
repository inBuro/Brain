# Каталог директив

Директивы — SOP для агента в Markdown. Это первоисточник «как запускать»: видео объясняет, зачем и где подвох,
директива задаёт точные фазы и формат. При ответе на «как сделать X» сверяться с файлом, а не с пересказом урока.

Общая механика всех директив модуля 2: сначала текстовые фазы с апрувом после каждой, только потом запись на канвас.
Причина — MCP-вызовы стоят денег и лимита, а текстовое дерево переделывается в разы быстрее.

## Системная инструкция агента

`GEMINI.md` / `Claude (1).md` / `bigPickle.md` — один и тот же текст под три среды
(Antigravity / VS Code + Claude Code / OpenCode). Урок 1.

Суть: трёхслойная архитектура.
- **Layer 1 — Directive**: SOP в Markdown в `directives/`, цели, входы, инструменты, выходы, edge cases.
- **Layer 2 — Orchestration**: сам агент, маршрутизация — читает директиву, вызывает скрипты в нужном порядке.
- **Layer 3 — Execution**: детерминированные Python-скрипты в `execution/`, ключи в `.env`.

Обоснование: 90% точности на шаге = 59% успеха на пяти шагах, поэтому сложность выносится в детерминированный код.
Принципы: сначала искать готовый инструмент в `execution/`; self-annealing (сломалось → починить → обновить директиву);
директивы — живые документы, но не перезаписывать их без спроса. `.tmp/` — промежуточные файлы,
деливеры живут в облаке (Sheets/Slides/Notion).

## Модуль 1 — цепочка артефактов

Каждая следующая директива читает выходы предыдущих. Порядок важен.

| Директива | Урок | Читает | Пишет |
| --- | --- | --- | --- |
| `directive_recursive_briefing.md` | 2 | вводные от заказчика | `brief.md` |
| `directive_quick_research.md` | 3 | `brief.md` | `competitive_analysis.md` |
| `directive_deep_research_prompt.md` | 3 | `brief.md`, `competitive_analysis.md` | `deep_research_prompt.md` (в Gemini Deep Research) |
| `directive_competitive_analysis.md` | 4 | бриф + оба ресёрча | `competitor_swot.md`, `competitor_features.md`, `competitor_ux_patterns.md`, `competitive_analysis_final.md` |
| `directive_ux_audit.md` | 5 | бриф, финальный конкурентный, `audit/screenshots/` | `audit/audit_report.md` |
| `directive_personas.md` | 6 | бриф, конкурентный, аудит | `personas.md` |
| `directive_simulated_interview.md` | 7 | всё выше + `personas.md` | `interview_<персона>.md` |
| `directive_scope_prioritization.md` | 8 | все артефакты | `features_list.md`, `prioritization.md`, `mvp_scope.md` |
| `directive_prd_notion.md` | 9 | все артефакты | `prd.md` + страница в Notion |
| `connect_notion_mcp.md` | 9 | — | подключённый Notion MCP |

Детали, которые чаще всего спрашивают:

- **Рекурсивный брифинг** — роль Senior UX Lead; три фазы: расширение (4–5 вопросов по категориям
  Пользователи / Функциональность / Тех. ограничения / UI-UX / Бизнес), углубление (2–3 раунда follow-up,
  после каждого summary «понятно / осталось выяснить»), консолидация. «Не знаю» уходит в открытые вопросы, не давить.
- **Конкурентный анализ** — четыре шага: SWOT по каждому (S/W про конкурента, O/T про нас) → матрица фич
  (✅ / ⚠️ / ❌, отдельно то, чего нет ни у кого) → UX-паттерны (рыночный стандарт, точки расхождения, рекомендации)
  → финальный документ с executive summary на 5–7 предложений.
- **UX-аудит** — когнитивный обход (цель / обнаружимость / связь / обратная связь на каждом шаге),
  10 эвристик Нильсена, серьёзность 4 Catastrophic → 3 Major → 2 Minor → 1 Cosmetic.
- **Персоны** — ровно три, по сегменту и сценарию на каждую; шесть блоков: роль и контекст, JTBD,
  паттерны поведения, раздражители и ограничения, триггер выбора, инсайты. Инсайты — ради них всё:
  формат «Потому что [факт] → нужно [решение]». Без фото и хобби; пункт, который не влияет на проектирование, удаляется.
- **Симуляция интервью** — агент говорит бытовым языком, не подыгрывает, примеряет на свой рабочий день,
  сам поднимает edge cases и задаёт встречные вопросы. По команде выходит из роли и выдаёт итоги:
  подтвердилось / новые инсайты / edge cases / противоречия / рекомендации.
- **Scope** — Must have только при трёх условиях: связь с JTBD primary-персоны, без неё основной сценарий невозможен,
  либо это table stakes. Won't have — осознанная позиция, а не забытые задачи. Scope MVP формулируется одним предложением.
- **PRD** — девять секций от Executive Summary до Roadmap; в Notion: оглавление, callout с саммари,
  toggle для user stories, callout с рисками, база «User Stories» с Board view по Priority, база «Feature Roadmap» с Table view.

## Модуль 2 — рельс в Figma

| Директива | Урок | Что делает |
| --- | --- | --- |
| `directive_figma_mcp.md` | 2.2 | установка MCP (правка `~/.claude.json`, перезапуск расширения, OAuth) + справочник инструментов read / write / FigJam / Code Connect |
| `directive_prd_to_sitemap.md` | 2.3 | PRD → инвентаризация экранов → sitemap → приоритеты → user flow в Mermaid → отрисовка на FigJam через `generate_diagram` |
| `directive_wireframes.md` | 2.4 | 3–5 экранов из sitemap → размеры → Markdown-структура каждого экрана → `use_figma`, один вызов на экран |
| `directive_ds_baseline.md` | 2.5 | сценарий A: бриф из пяти вопросов → foundation в Markdown (три слоя токенов) → Variables + фундамент-секция и семь базовых компонентов → `ds/CONTRACT.md` |
| `directive_ds_scan.md` | 2.5 | сценарии B и C: индексирование готовой ДС в `ds/foundation.md` и `ds/components.md` + тот же контракт |
| `directive_grow_ui_kit.md` | 2.6 | пять фаз read → brief → md → canvas → write+audit; пакеты по 2–3 компонента |
| `directive_component_variants.md` | 2.7 | матрица variants × states × sizes, single или bulk; новые Semantic-токены под состояния с alias к Primitive |
| `directive_final_screens.md` | 2.8 | wireframe + каталог компонентов → composition map в md → экран на канвасе из instance |
| `directive_screens_audit.md` | 2.10 | read-only аудит по шести проверкам; автофиксы только через `--fix` и явный апрув |

Детали, которые чаще всего спрашивают:

- **Три слоя токенов**: Primitive (сырые значения) → Semantic (смысл: поверхности, текст, обводки, состояния)
  → компонентные. Semantic ссылается на Primitive через alias, прибитый hex запрещён контрактом.
- **`ds/CONTRACT.md`** — главное правило: нет компонента в ДС → сначала завести его в ДС, потом использовать на экране.
  Плюс указатель на ДС в корневом `CLAUDE.md` проекта и правила синхронизации Figma ↔ `ds/*.md`.
- **Шесть проверок `screens_audit`**: отвязанные элементы вместо instance, прибитый hex без Variable,
  дубликаты компонентов, неиспользуемые компоненты, расхождения в состояниях, покрытие состояний (edge cases).
- **`final_screens`, восемь принципов**: sizing — это смысл, а не размер; только instance; цвета и размеры через Variables;
  иконки — реальные SVG, не серые квадраты; тени из foundation; Dashboard не может быть пустым;
  структурированная мета вместо plain text через точки; повторяющийся блок — компонент в UI-ките, а не локальная сборка.
- **Где AI плывёт** (по урокам): матрица от 25 ячеек, focus ring, loading с анимацией, Auto Layout на длинных пакетах,
  empty states и иконки в финальных экранах, каша на больших sitemap и выдуманные экраны.

## Модуль 3 — Visual Engineer

Директив всего две: модуль в основном про инструменты, а не про агента.

| Директива | Урок | Что делает |
| --- | --- | --- |
| `directive_brand_visual_direction.md` | 3.5 | собирает `brand-direction.md` — визуальный манифест продукта, который подставляется в стилевые поля JSON-промпта |
| `directive_video_storyboard.md` | 3.9 | из контекста продукта делает `video_storyboard.md`: промпт Сетки 4K на три ключевых кадра + два промпта image-to-video |

Детали, которые чаще всего спрашивают:

- **Главный принцип brand-direction** — работаем не через имена эстетик («risograph», «brutalist», «cinematic»),
  а через корневые свойства визуала. Имя стиля — это пониженное разрешение, под него подпадает усреднённый AI-сахар.
- **Семь корневых свойств**: tactile materiality (что физически в кадре), restricted saturated palette (2–3 конкретных цвета),
  light as graphic element (свет строит композицию, а не освещает), compositional courage (обрезка, close-up, асимметрия),
  grain and texture (кадр не стерильный), emotional density (3–5 конкретных прилагательных),
  refusal of AI-default. Каждое либо прописано конкретно, либо явно отказано с обоснованием.
- **Anti-patterns директивы** — длинный явный список того, что агент не должен предлагать даже из лучших побуждений:
  неоновые градиенты, дефолтный AI-закат, голограммы в руках, cyber-city, liquid metal, clay render,
  glassmorphism как главный приём, «futuristic», «modern minimalist», «premium feel» и имена эстетик без раскрытия.
- **Цвета берутся из `ds/foundation.md`** и не переинтерпретируются; на выходе — одна страница, а не манифест,
  и обязательный готовый style-блок плотным абзацем для подстановки в JSON.
- **Сетка 4K** (`video_storyboard`) — одно 4K-изображение, разбитое на три пронумерованные ячейки с общим стилем
  и светом; так весь сет выходит консистентным. Промпты кадров — на английском.
- **Клипы сшиваются встык**: клип A — кадр 1 → кадр 2, клип B — кадр 2 → кадр 3, конец первого равен началу второго.
  Кадр 2 должен быть честной серединой, иначе переходы рвутся. В промптах перехода описывается только движение.

## Модуль 4 — AI Prototyper & Agents

Здесь директивы устроены строже, чем во втором модуле: у каждой есть предусловие, ключевой принцип,
явная граница «что НЕ делаем», self-check и раздел «Грабли». Почти все — переиспользуемые:
повторный запуск не сносит сделанное, а синхронизирует или наращивает.

| Директива | Урок | Что делает |
| --- | --- | --- |
| `directive_react_base .md` | 4.3 | разворачивает Vite + React + TypeScript и собирает зеркальную копию ДС: токены из `foundation.md`, компоненты из `components.md`, плюс `Showcase.tsx` |
| `directive_storybook .md` | 4.4 | собирает каталог компонентов в Storybook: stories на все компоненты (CSF3 + autodocs), foundation-страница, песочницы |
| `directive_handoff .md` | 4.4 | заливает проект на GitHub и отдаёт ссылку для передачи в разработку |
| `directive_screens .md` | 4.5 | собирает один экран из базы по ссылке на фрейм Figma, регистрирует его в реестре и выводит на навигационную страницу-индекс |
| `directive_wire .md` | 4.6 | оживляет экраны: навигация, слой мок-данных, формы, состояния и edge-cases |
| `directive_deploy .md` | 4.7 | публикует прототип — путь A на Vercel / Netlify / Cloudflare, путь B на свой VPS — и пишет живую ссылку в `PROJECT.md` |
| `directive_dashboard .md` | 4.8 | подключает бандл `dashboard/`: трекер в прототип, сборщик событий на сервер, дашборд метрик |
| `directive_release_environment .md` | 4.9 | сворачивает накопленные директивы и историю работы в AI-среду: навыки, субагенты, оркестрация |

Детали, которые чаще всего спрашивают:

- **«Имя = якорь»** — ключевой принцип `react_base`: `surface-default` в Figma → `--surface-default` в коде,
  `Button` в Figma → `<Button>` с теми же вариантами. На общих именах держится зеркало, каталог, экраны и синхронизация.
- **Стек** — Vite + React + TypeScript, токены как CSS-переменные, стили компонентов на CSS Modules
  поверх семантических переменных. Два слоя токенов ровно как в Figma: семантика ссылается на примитив через `var(...)`.
- **Открытая база вместо своей**: если ДС основана на shadcn или подобной, компоненты берутся из библиотеки,
  а её тема перекрывается своими семантическими токенами — ручная сборка компонентов пропускается.
- **Цвет не зашивается в типографический класс** — как и в Figma, TextStyle не несёт цвет.
- **Граница `screens`**: собирается только раскладка и статичный вид. Ни логики, ни обработчиков, ни слоя данных,
  ни рабочих форм. Причина названа прямо: если попросить «собери и заодно оживи», агент навесит поведение сразу,
  и следующий шаг останется без работы.
- **Ссылка на фрейм, а не на файл**: по ссылке на корень файла MCP отдаёт только первую страницу.
- **Чтение дизайна по частям**: `get_metadata` для карты структуры, `get_design_context` по секциям, `get_screenshot` для сверки глазами.
- **Доменные блоки** (ServerCard, StatCard) собираются как локальные композиции экрана в `parts/`, в базу не тащатся;
  если такой блок встретился на втором экране — повод вынести в базу.
- **Навигационная страница-индекс обязательна**: реестр `src/screens/registry.ts` — единый источник и для роутинга,
  и для плиточного индекса, чтобы экраны не лежали россыпью файлов.
- **Четыре составляющие оживления**: навигация, слой мок-данных, формы, состояния по действию (загрузка, пусто, ошибка, успех).
  Бэкенда нет — только мок; деплой и метрики вынесены в отдельные директивы.
- **SPA-маршрутизация** — главное, что настраивается при деплое обоими путями: любой неизвестный путь отдаёт `index.html`,
  иначе прямые ссылки на внутренние экраны дают 404. Пароли и токены транзиентные — не в файлы и не в `PROJECT.md`.
- **Почему сбор метрик живёт на своём сервере**: события копятся во времени, а на Vercel и Netlify статика
  и короткие функции без постоянного диска. Прототип может быть где угодно, данные — всегда на своём VPS.
- **Два пути дашборда**: прототип на своём сервере — трекер шлёт на `http://<IP>:<порт>`; прототип на https-сервисе —
  браузер заблокирует http как mixed content, мостом служит бесплатный туннель ngrok.
- **`release_environment` читает живую документацию Anthropic** при каждом запуске, а не зашитый снимок,
  и собирает среду под то, как пользователь реально работал, по локальной истории. Старое архивируется, не удаляется.
