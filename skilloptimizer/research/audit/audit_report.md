# UX-аудит: Skill Optimizer

> Методология: 10 эвристик Нильсена + когнитивный обход, `directive_ux_audit.md`. Аудит смотрит на продукт как на потенциально публичный (через призму брифа и `competitive_analysis_final.md`) — многие находки не мешают текущему единственному пользователю (он же автор, знает продукт наизусть), но станут реальным трением для нового человека.
>
> **Оговорка по методу:** шаг 1 (главный список) верифицирован живым скриншотом (`screenshots/01_main_list.png`), сделанным через реальный клик по иконке в мунбаре. Состояния Edit/Delete-confirm описаны по коду (`DescriptionPopover.swift`), который я знаю построчно из работы над ним в этой же сессии.
>
> **Находка №1 (попап описания отсоединяется от строки) — понижена в приоритете 2026-08-29.** Воспроизведена дважды через автоматизированный клик, включая один раз через настоящий синтетический mouse-клик (не AX-скриптинг) — скриншот-пруф в `screenshots/02_description_popover_detached.png`. Тем не менее владелец не встречает этого в реальном повседневном использовании и попросил не приоритизировать это дальше. Находка остаётся задокументированной (техническая причина правдоподобна — `.popover` внутри `MenuBarExtra(.window)`), но не в топе рекомендаций — см. обновлённую сводку.

## Когнитивный обход

**Шаг 1 — открыть мунбар.** Цель: увидеть плотность использования скиллов. Обнаружимость иконки — ок (стандартная позиция в строке меню). Связь «иконка → список активности» — не очевидна без знания контекста продукта (иконка `chart.bar.fill` не намекает на «Claude Code skills» специфично; для случайного человека это может быть любой чарт-трекер). Обратная связь — мгновенная (попап открывается сразу).

**Шаг 2 — прочитать список.** Цель: понять, что часто используется. Обнаружимость сортировки/таймфрейма — ок, но кнопка сортировки «321»/«ABC» требует наведения (tooltip) или знания конвенции, чтобы понять, что это переключатель, а не статичный лейбл. Связь «роутер без счётчика, но высоко в списке» → не очевидна (находка №4). Обратная связь на смену таймфрейма/сортировки — мгновенная, без анимации моргания (хорошо).

**Шаг 3 — открыть скилл.** Цель: посмотреть, почему скилл (не) срабатывает. Обнаружимость — chevron `›` есть, но семантически неоднозначен (находка №3). Связь «клик → появится инфо-попап» — при наблюдавшемся баге позиционирования (находка №1) эта связь буквально разрывается: результат клика визуально не связан с местом клика.

**Шаг 4 — отредактировать триггеры.** Цель: добавить/убрать фразу. Обнаружимость «+ Text-trigger» — хорошо (оранжевый акцентный цвет). Обратная связь на удаление триггера (✕) — операция происходит молча, без какого-либо подтверждения или последующего сообщения (находка №2). Обратная связь на сохранение через «+ Text-trigger» — по коду не появляется вообще (находка №5, самая серьёзная находка аудита).

**Шаг 5 — удалить скилл.** Цель: заархивировать неиспользуемый скилл. Обнаружимость — «Delete Skill» в углу, текст явный. Связь и обратная связь — хорошо: два шага подтверждения, `deleteError` показывает причину при неудаче.

## Эвристическая оценка

1. **Видимость состояния системы** — частично нарушена: «Saved» после сохранения триггера не успевает отрендериться (находка №5); ранжирование роутеров по максимуму среди детей не отражено видимым числом на самой строке роутера (находка №4).
2. **Соответствие реальному миру** — нарушена в одном месте: chevron `›` рядом с именем скилла в общем списке UI-конвенций обычно означает «раскрыть/свернуть», здесь означает «открыть попап с информацией», при этом сама иерархия роутер→подскиллы никогда не сворачивается (находка №3).
3. **Свобода и контроль** — хорошо для Delete Skill (двухшаговое подтверждение, Cancel есть); слабо для удаления отдельного триггера — нет отмены, нет подтверждения (находка №2).
4. **Консистентность и стандарты** — три асимметрии: (а) Delete Skill подтверждается, удаление триггера — нет; (б) успех сохранения не показывается, ошибка — показывается; (в) `.popover` в теории должен вести себя как системный поповер с якорем и стрелкой, но внутри `MenuBarExtra(.window)` этого не происходит (находка №1).
5. **Предотвращение ошибок** — Delete Skill соблюдает (архивация, не удаление; подтверждение); удаление триггера — нет (находка №2).
6. **Узнавание вместо запоминания** — в целом хорошо: вся нужная информация (счётчики, триггеры) видна на экране без необходимости что-то держать в памяти.
7. **Гибкость и эффективность** — есть быстрые действия (клик по `+N` для acknowledge), но нет шорткатов для частых power-user операций (например, массовая архивация нескольких найденных неиспользуемых скиллов сразу — только по одному).
8. **Минималистичный дизайн** — сильная сторона продукта: минимум хрома, текст вместо иконок там, где можно, эта работа уже проделана в проекте.
9. **Помощь с ошибками** — `deleteError` показывает `localizedDescription` — техническое сообщение файловой системы, не человекочитаемая рекомендация (например, «нет прав на запись» вместо «Permission denied»). Минорная находка, не включена отдельной строкой в таблицу ниже (cosmetic, не набрала веса).
10. **Помощь и документация** — отсутствует полностью: нет онбординга, нет объяснения в самом приложении, что такое «плотность скиллов», зачем сканируются файлы, что данные не покидают машину (находка №2 в контексте брифа/позиционирования из `competitive_analysis_final.md`).

## Сводка

- **Критические проблемы (severity 4):** нет.
- **Серьёзные проблемы (severity 3):** #2 (удаление триггера без подтверждения/отмены), #4 (невидимый критерий ранжирования роутера), #5 (сообщение об успехе технически невидимо — воспроизводится по коду со 100% уверенностью). #1 понижено — см. оговорку выше.
- **Общая оценка.** Сильная сторона продукта — минимализм и приватность (уже отмечено эвристикой #8, и подтверждено конкурентным анализом: ни один из 8 исследованных конкурентов не даёт того же уровня privacy-by-default). Системная слабость — **асимметрия обратной связи**: везде, где действие может провалиться, есть явная сигнализация (`deleteError`, error-текст в `AppendField`), но там, где действие успешно — сигнал либо отсутствует, либо технически не успевает отрендериться. Это системный паттерн, не единичная случайность (находки №2 и №5 — одна и та же болезнь в двух местах).
- **Топ-5 рекомендаций:**
  1. Исправить невидимость «Saved» в `AppendField` — самая дешёвая по трудозатратам и самая объективно доказанная находка (баг в коде, не гипотеза).
  2. Добавить лёгкое подтверждение/undo на удаление триггера — привести к консистентности с Delete Skill.
  3. Показать приглушённый «максимум среди детей» счётчик у роутеров без собственных вызовов — недорогая правка, устраняющая уже дважды случившуюся путаницу.
  4. Перед публичным релизом — добавить минимальное объяснение privacy-модели в UI (перенять паттерн WakaTime/AgentPeek — не переносить их усложнённый онбординг, только сам факт объяснения «данные не покидают машину»).
  5. (Снято с приоритета) Позиционирование `.popover` внутри `MenuBarExtra(.window)` — задокументировано, но не в фокусе: владелец не наблюдает это в реальном использовании.
