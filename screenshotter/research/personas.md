# Персоны — Screenshotter

Три персоны выбраны так, чтобы вместе покрыть обе гипотезы (план A и план B) и
главный открытый вопрос модели монетизации: (1) массовый casual-сегмент — тест плана
A, (2) продвинутый agentic-сегмент — тест плана B, (3) бюджетно-ориентированный
сегмент — стресс-тест самой идеи платности, независимо от плана.

---

## 1. Оля — фронтенд-разработчица, работает в Cursor

**Роль и контекст.** Solo/small-team фронтендер. Основной инструмент — Cursor,
плюс Claude.ai в браузере для архитектурных вопросов. Screenshotter встанет в её
менюбар рядом с уже привычными тулами, не как отдельный ритуал.

**Job-to-be-Done.** Нанимает продукт, чтобы скриншот бага в UI не ронял AI-сессию и
не заставлял пересказывать контекст заново. Возникает в разгар долгой
debugging-сессии, на десятом скриншоте подряд. Успех — сессия не обрывается, не
приходится копипастить историю в новый чат.

**Паттерны поведения.** Скриншотит по несколько раз в час в активные дни отладки.
Сейчас пользуется системным ⇧⌘4 — отдельного тула нет. Вставляет сразу в
Cursor/Claude chat.

**Раздражители и ограничения.** Регулярно видит «context limit» / «session died»
(подтверждено deep research, п.2 — «session died / context limit hit / forced new
session»). Не готова настраивать MCP или skill — не хватает времени и не её профиль
задач (см. SWOT SlimSnap: «требует поддержки... не работает из коробки»). Бюджет
скромный, но готова платить за реальную экономию времени. Боится, что новый тул
конфликтует с уже привычным хоткеем ⇧⌘4 — и это реальный риск: он совпадает с
дефолтным хоткеем Screenshotter (см. `audit_report.md`).

**Триггер выбора.** Найдёт через поиск в духе «screenshot claude code context limit»
(источники deep research именно такие). Попробует, если установка меньше минуты и
без конфигурации. Останется, если реально перестанет видеть «session died».
Dealbreaker — конфликт хоткея с системным или необходимость MCP-настройки.

**Инсайты.**
- Потому что она не готова настраивать MCP → в плане B MCP должен быть опцией для
  продвинутых, а не обязательным шагом первого запуска.
- Потому что дефолтный хоткей совпадает с системным (аудит) → сменить дефолт при
  установке, не полагаться на то, что пользователь сам полезет в настройки.
- Потому что узнаёт о риске только когда сессия уже оборвалась → индикатор режима
  перед захватом (топ-рекомендация аудита) снимает именно её боль.
- Потому что мерилом успеха для неё служит «больше не вижу session died» → нужна
  явная лёгкая обратная связь вроде «оптимизировано, сессия в безопасности», не
  тихая работа в фоне.

## 2. Стас — инженер, строит собственных AI-агентов

**Роль и контекст.** Senior/staff-инженер, автоматизирует рабочие процессы через
Claude Code и собственные MCP-серверы. Активно следит за agentic tooling, вероятно
уже пробовал Screentack или SlimSnap.

**Job-to-be-Done.** Нанимает продукт, чтобы агент сам запрашивал и получал точный,
откалиброванный скриншот без участия человека — как часть автономного цикла, не
разовое ручное действие. Возникает при построении Computer Use-подобных пайплайнов.
Успех — агент не промахивается кликами и не тратит токены впустую без ручного
вмешательства.

**Паттерны поведения.** Ежедневно работает с MCP-серверами, следит за GitHub trending
в этой нише — сам нашёл бы Screentack/SlimSnap/pxpipe без наводки.

**Раздражители и ограничения.** Подтверждено deep research, п.6: серверное
масштабирование Retina-скриншотов сдвигает координаты кликов на 20–40px — злится,
когда агент промахивается по кнопке из-за некалиброванного снимка. План A («просто
ресайз») для него выглядит игрушечным — не решает задачу точности. Технически
способен настроить что угодно сам, бюджет не ограничение, если решает задачу.
Боится получить поверхностный ресайзер без реальной агентской интеграции — ровно
риск, зафиксированный в SWOT плана A.

**Триггер выбора.** Найдёт через GitHub/Product Hunt/технические треды про MCP.
Попробует, если есть явный MCP-сервер и нормализация под Computer Use. Останется,
если измеримо снижает промахи кликов. Dealbreaker — отсутствие MCP и нормализации
координат: план A для него сразу мимо.

**Инсайты.**
- Потому что его реальная боль — промахи кликов, не только токены → нормализация под
  1024×768/1280×720 (уникальная фича плана B) обязательна, не опциональна.
- Потому что сам технически способен настроить MCP → MCP-сервер можно делать
  first-class для этого сегмента, не упрощать в ущерб глубине.
- Потому что уже знает про Screentack → нужен явный, а не подразумеваемый
  дифференциатор против него.
- Потому что план A для него «игрушка» → этот сегмент полностью игнорирует план A;
  весь его интерес — валидация плана B, не A.

## 3. Женя — инди-разработчик, экономит на всём тулинге

**Роль и контекст.** Соло-разработчик/фрилансер, работает с несколькими AI-чатами и
Claude Code. Принципиально предпочитает open-source и бесплатные инструменты, сам
пишет мелкие скрипты под себя.

**Job-to-be-Done.** Нанимает (бесплатный) способ закрыть проблему, не платя за то,
что «можно написать самому за 20 минут» (формулировка из deep research, п.5).
Возникает при столкновении с той же болью — но первая реакция не «купить», а
«поискать бесплатное» или «написать скрипт».

**Паттерны поведения.** Активно читает GitHub/Reddit, вероятно уже нашёл Image
Resizer for Claude Code или pxpipe. Ставит Shottr вместо CleanShot X.

**Раздражители и ограничения.** Deep research, п.5: «склонность к поиску
Open-Source альтернатив», потолок готовности платить за узкую утилиту — $15–20.
Бесит, когда нишевая функция монетизирована, хотя реализуема в 20 строках кода.
Бюджет = 0 в идеале, высокие технические навыки, время не проблема — готов
повозиться, чтобы не платить.

**Триггер выбора.** Найдёт продукт тем же поиском, что и Оля, но сразу сравнит с
бесплатными альтернативами. Попробует, если есть бесплатная версия/триал. Останется,
только если увидит то, что скриптом не собрать (глубокая MCP-интеграция, нормализация
координат, аккуратный нативный UX). Dealbreaker — цена без внятного «почему не
бесплатно».

**Инсайты.**
- Потому что для него любой платный функционал должен быть невоспроизводим
  bash-скриптом → план A («просто ресайз») для него прямой сигнал «не покупать, сам
  напишу sips-скрипт».
- Потому что бесплатные прямые аналоги реально существуют (Image Resizer, pxpipe) →
  цена оправдана только тем, чего скрипт не даёт — это план B, не A.
- Потому что он технически способен на альтернативу → реалистичная конверсия для
  этого сегмента — только через open-source путь (вариант Gemini «A») или free tier.
- Потому что ключевой вопрос для него — «почему не бесплатно» → PRD должен отвечать
  на него явно, не умалчивать цену.
