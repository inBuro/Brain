# UX-аудит: Screenshotter

> Скриншоты не удалось снять: UI-автоматизация через `System Events` не достучалась
> до menu bar статус-айтема приложения (Accessibility разрешена, но иерархия меню не
> вернулась — вероятно, специфика NSStatusItem-приложения без Dock-иконки). Аудит
> построен на задокументированном в `wiki/internals.md` и `wiki/log.md` поведении —
> это первичный источник по правилам проекта, точнее пересказа. Места, требующие
> визуальной сверки, помечены явно.

## Когнитивный обход

**1. Первый запуск — иконка появляется в трее (SF Symbol `camera.viewfinder`).**
Цель — непонятна без предварительного знания: нет онбординга, коучмарка, приветствия.
Обнаружимость — иконка заметна, но неотличима от системных иконок камеры других
приложений, никакого текста/бейджа. Связь — если пользователь сам ставил
приложение, свяжет; случайный пользователь — нет. Обратная связь — отсутствует.
→ **Спотыкается**, но некритично для целевой аудитории (сама себе ставит утилиты).

**2. Клик по иконке → меню.** Цель — стандартный macOS-паттерн, ожидаемо понятно.
Обнаружимость — пункты меню видны сразу. Связь — названия «Full-size screenshots» /
«AI-optimized screenshots» понятны по смыслу. Обратная связь — **не подтверждено**,
есть ли чекмарк у активного режима в самом меню (требует визуальной сверки).
→ Флаг видимости состояния.

**3. «Add window shadow».** Цель/обнаружимость/связь — понятны по названию. Обратная
связь — из `internals.md`: тень **не действует на rectangle-drag**, только на захват
окна — это ограничение нигде не объясняется в UI. → **Спотыкается**: пользователь
включит тень, сделает выделение прямоугольником, тени не будет, и не поймёт почему.

**4. Shortcut (перезапись хоткея).** Цель понятна. Обнаружимость/связь — ясны. Ранее
был баг «recording a new shortcut killed the app» (исправлен) — сам факт говорит о
хрупкости этого шага; **не подтверждено**, есть ли явная визуальная индикация
«режим записи активен».

**5. Нажатие хоткея → crosshair → выделение.** Цель/обнаружимость/связь — стандартный
системный паттерн `screencapture -i`, знаком большинству пользователей Mac. Обратная
связь — **сильная сторона**: после захвата приходит нотификация с режимом и
размерами. Но: **дефолтный хоткей ⇧⌘4 идентичен системному macOS-хоткею**
«скриншот выделения в буфер» — пользователь не может на глаз отличить, что сработал
именно Screenshotter, а не системная утилита, и в какой она сейчас режим (Full-size
vs AI-optimized) — узнаёт только постфактум, из нотификации, когда снимок уже сделан.

**6. Esc для отмены.** Задокументировано явно: «no file on disk → silent exit, not an
error». Это правильный паттерн — не проверено визуально, но подтверждено кодом/логом.

## Эвристическая оценка

1. **Видимость состояния системы** — плюс: пост-капча нотификация с режимом и
   размерами. Минус: нет индикации активного режима *до* или *во время* захвата —
   ровно в момент, когда решение уже нужно принимать.
2. **Соответствие реальному миру** — минус: «Add window shadow» не сообщает о своём
   скрытом ограничении (window-only). Плюс: паттерн crosshair — родной для macOS.
3. **Свобода и контроль** — плюс: Esc = тихий выход без ошибки. Минус: отменить сам
   захват после выделения области нельзя (ограничение системного `screencapture`,
   не самого приложения).
4. **Консистентность и стандарты** — плюс: нативный паттерн, хоткей в стиле
   системных. Минус: хоткей по умолчанию **совпадает** с системным — маскируется под
   стандартную функцию вместо того, чтобы отличаться от неё.
5. **Предотвращение ошибок** — минус: нет предупреждения при первом использовании о
   том, что AI-optimized режим необратимо режет разрешение — риск случайно потерять
   качество тому, кому нужен был full-size.
6. **Узнавание вместо запоминания** — минус, основной системный: пользователь должен
   **помнить**, какой режим сейчас активен, чтобы не гадать по результату постфактум.
7. **Гибкость и эффективность** — плюс: Option-click переключает режим без захода в
   меню; single-instance guard; open at login — низкое трение для опытных пользователей.
8. **Минималистичный дизайн** — плюс, заметный: меню короткое (7 пунктов), нет
   визуального шума в духе CleanShot X/Xnapper (см. `competitor_ux_patterns.md`).
9. **Помощь с ошибками** — плюс: тихий Esc без ложной ошибки. Минус: тихий сбой
   ожидания у shadow-тумблера (см. эвристику 2) — тоже без сообщения.
10. **Помощь и документация** — минус: никакой встроенной помощи в самом приложении;
    вся документация — в `~/Brain` для разработчика, не для конечного пользователя.

## Сводка

- **Критические (4):** нет.
- **Серьёзные (3):** хоткей-конфликт с системным, отсутствие индикатора режима в
  момент захвата, необъяснённое ограничение shadow-тумблера.
- **Общая оценка.** Сильные стороны — минимализм меню (лучше почти всех
  конкурентов), качественная пост-факт обратная связь (нотификация с режимом и
  размерами — редкость среди конкурентов), быстрые шорткаты для опытных
  пользователей (Option-click). Системная слабость — недостаточная видимость
  состояния именно **в момент принятия решения** (перед/во время захвата), а не
  постфактум. Это бьёт ровно в ту боль, ради которой продукт существует: пользователь
  должен быть уверен, что снимок уже оптимизирован под AI, не проверяя результат
  задним числом.

**Топ-5 рекомендаций:**

1. Визуальный индикатор активного режима в момент захвата (HUD у crosshair) — не
   закрыт ни одним из семи конкурентов; для плана B естественно объединяется с
   индикатором стоимости в токенах в одном UI-моменте.
2. Развести дефолтный хоткей с системным ⇧⌘4, чтобы приложение не маскировалось под
   стандартный macOS-скриншот.
3. Объяснить ограничение «Add window shadow» прямо в интерфейсе, не оставлять
   пользователя гадать постфактум.
4. Взять паттерн SlimSnap (конкретные цифры вместо абстракций) — если добавлять
   индикатор экономии в плане B, делать его числовым.
5. Не повторять перегруженность CleanShot X/Xnapper при добавлении новых пунктов
   (MCP, PII и т.д. из плана B) — короткое меню уже сильная сторона.
